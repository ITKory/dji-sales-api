# Бизнес-правила и проверочные примеры

Правила статусов и основные формулы заданы пользователем и обязательны. Остальные детали явно являются проектными решениями.

## Статусы и метрики

| Статус | Revenue/Cost/GP/Margin | Число продаж/Average Check | Рейтинги | Recent Sales |
|---|---|---|---|---|
| Paid | Участвует | Участвует | Участвует | Показывать |
| Cancelled | Исключить | Исключить | Исключить | Показывать |
| Refunded | Полностью исключить | Полностью исключить | Полностью исключить | Показывать |

Refunded — полная отмена вклада продажи в чистые метрики, а не отрицательная продажа и не повторное вычитание суммы из набора Paid. Cost также учитывается только у Paid. Частичные возвраты, возвратная комиссия, налоги, доставка, скидки отдельными полями не заданы; UnitSalePrice предполагается конечной фактической ценой.

Для выбранного набора Paid-продаж:

```text
Revenue     = SUM(item.Quantity * item.UnitSalePrice)
Cost        = SUM(item.Quantity * item.UnitCost)
GrossProfit = Revenue - Cost
SalesCount  = COUNT(DISTINCT Sale.Id)
MarginRatio = Revenue == 0 ? 0 : GrossProfit / Revenue
AverageCheck = SalesCount == 0 ? 0 : Revenue / SalesCount
```

Доменная Margin — отношение. API margin = MarginRatio * 100 (0.42 → 42), потому что frontend добавляет `%`, но не умножает на 100. Расчёт суммарной маржи/среднего чека всегда из суммарных числителя и знаменателя, не среднее арифметическое маржи/чека групп.

Расчёты C# decimal; значения Revenue/Cost/GP точны в центах. Average Check и API percentages округляются до двух знаков в конце, MidpointRounding.AwayFromZero; delta рассчитывать до округления исходных метрик. Нельзя обрезать отрицательную прибыль или margin; при нулевой выручке margin=0 даже при положительной себестоимости. Бесплатный Paid-чек входит в SalesCount.

## Refunded — окончательное правило

**Принято и обязательно для всех будущих аналитических запросов:** Refunded — полностью возвращённый чек. Такой Sale и все его SaleItem исключаются из Revenue, Cost, Gross Profit, Margin, SalesCount, Average Check, рейтинга/лучшего менеджера, категорий, продуктов и дневной динамики. Единый предикат аналитики: `Sale.Status == SaleStatus.Paid`.

- Не создавать отрицательную продажу, отрицательные quantity/цены и не вычитать Refunded ещё раз из суммы Paid.
- Исходные позиции, цены, себестоимость, SaleDate и сумма чека сохраняются для истории. В Recent Sales возврат виден со status=Refunded, amount=исходная сумма, признанная grossProfit=0.
- Если Paid меняет статус на Refunded, его вклад полностью исчезает из **исходного периода SaleDate**, включая Previous Period. Отдельной отрицательной проводки в день возврата нет; отчёт отражает текущее состояние продаж, а не бухгалтерское движение денег.
- Частичные возвраты, комиссии и невозмещённая себестоимость не моделируются. Для них потребуется отдельное изменение требований/модели.
- Пример: оплаченные чеки на 100 и 200; второй полностью возвращён. Итог Revenue=100, SalesCount=1, AverageCheck=100; прибыль и себестоимость только первого. Если возвращены оба — все эти метрики и Margin равны 0, рейтинг пуст, обе строки остаются в Recent Sales.

В sales-demo-v1 есть 205 Refunded с положительными исходными суммами и неизменёнными историческими ценами. Отрицательная прибыль редких Paid-позиций — допустимый убыток, не способ представить возврат.

## Периоды и включительные границы

Даты понимаются в Reporting__TimeZone (проектное значение Europe/Belgrade), today определяется единым TimeProvider один раз на запрос.

| Preset | from | to |
|---|---|---|
| today | today | today |
| last7 | today − 6 календарных дней | today |
| last30 | today − 29 календарных дней | today |
| thisMonth | первое число текущего месяца | today (MTD) |
| lastMonth | первое число прошлого месяца | последнее число прошлого месяца |
| custom | входное from | входное to |

Обе границы включительны. В SQL переводить в UTC локальное начало from и начало дня после to, затем `SaleDate >= startUtc AND SaleDate < endExclusiveUtc`. Не сравнивать с искусственным 23:59:59.999; не добавлять фиксированные 24 часа к UTC в дни перехода DST. Группировка графика и фильтр используют одну timezone. Продажи привязаны к SaleDate; отдельной PaidAt нет (допущение).

```text
N = to.DayNumber - from.DayNumber + 1
previousTo = from - 1 календарный день
previousFrom = from - N календарных дней
```

Previous Period той же длины и непосредственно предшествует выбранному. Для 1–23 сентября это 9–31 августа (23 дня), а не 1–23 августа. Для августа 2026 (31 день) — 1–31 июля. Равенство длины календарное, не в часах.

В frontend daysInRange = round((to-from)/86400000)+1: для today со startOfDay/endOfDay получает **2**, для last7 — **8**, для last30 — **31**. Генераторы могут добавлять лишний день; эту ошибку нельзя переносить в backend. Custom из календаря содержит полночь конечного дня, которую сервер должен понимать как весь этот день.

## Изменения относительно Previous Period

Для Revenue, GP, SalesCount, Average Check и GP лидера/менеджера:

- previous > 0: `(current - previous) / previous * 100`.
- previous = 0 и current = 0: 0.
- previous = 0 и current != 0: null (нет базы; не 100%, не Infinity).
- previous < 0: null; абсолютное изменение доступно через current−previous, процент вводил бы в заблуждение при убытке.
- marginDelta = margin − marginPrev в **процентных пунктах**, не относительных процентах.

Nullable changes — предлагаемое расширение исходных TS number; frontend должен показывать «—» без стрелки. BestManager при отсутствии текущих Paid не выбран, delta=null независимо от прошлого периода.

## Рейтинги и разрезы

- Лидер KPI: наибольшая Gross Profit среди менеджеров с хотя бы одной текущей Paid-продажей. При убытках у всех победит наименьший убыток; менеджер без продаж не выигрывает у убыточного.
- Рейтинг: sortBy DESC, затем другая из GP/AvgCheck DESC, затем id ASC. Для bestManager используется тот же порядок grossProfit, avgCheck, id. Не округлять значения до сортировки.
- GP Change/AvgCheck Change сравнивают одного и того же менеджера в двух периодах. Предыдущий победитель не подменяет предыдущую метрику текущего лидера.
- Comparison включает выбранных существующих менеджеров даже без продаж; для них нули. Рейтинг пуст, если в периоде нет Paid.
- Категории: суммы Paid-позиций по CategoryIdAtSale; доли Revenue и GP frontend вычисляет отдельно. При нулевом знаменателе доля=0; при отрицательной общей GP процентную долю прибыли лучше показывать «—», абсолютную GP сохранять.
- Продукты: Revenue DESC, затем GP DESC, затем составной id ASC; default top 8. При смене категории один ProductId может иметь две строки (явно см. API).
- Dynamics: каждый календарный день выбранного диапазона, нули для пропусков, все три метрики одновременно. Суммы дневных Revenue/GP/SalesCount равны KPI.
- Sparkline: ежедневные агрегаты той же выборки; margin/avgCheck вычисляются за каждый день, bestManager — GP текущего лидера за день. Нельзя суммировать дневной Average Check для итогового KPI.
- Recent Sales: все статусы, исходная amount, GP=0 для Cancelled/Refunded. Это не дополнительный агрегат revenue и сумма страницы не обязана равняться KPI.

## Проверочные случаи

1. Paid A: 2×100 при cost 60; Paid B: 1×50 при cost 20. Cancelled и Refunded произвольной суммы рядом. Итог Revenue=250, Cost=140, GP=110, SalesCount=2, Margin=44%, AvgCheck=125; не 3 продажи по количеству единиц.
2. Только Cancelled/Refunded: все финансовые KPI и SalesCount=0, Average Check=0, Margin=0, bestManager=null; Recent Sales не пуст.
3. Paid с price=0, cost=10: Revenue=0, GP=−10, Margin=0, SalesCount=1, Average Check=0.
4. Revenue previous=200,current=250 → delta=25%; margin previous=40,current=44 → marginDelta=4 pp. 0→0 даёт 0; 0→250 даёт null; GP −100→50 даёт null.
5. Today: ровно один день и один предыдущий день; last7 — семь; thisMonth на первом числе — один; lastMonth через январь и високосный февраль.
6. Sale ровно startUtc включена; ровно endExclusiveUtc исключена; последняя микросекунда to включена. День DST не теряет/добавляет календарный день.
7. JOIN нескольких позиций не увеличивает SalesCount; суммы категорий/менеджеров равны общим суммам, сумма ограниченного top-products может быть меньше.
8. Возврат Paid A исключает весь A из исходного периода, без отрицательной проводки в новом периоде.
9. Равные рейтинги стабилизируются id, лидер без текущих продаж не выбран, bestManagerPrev относится к тому же менеджеру.
10. Пустая страница, менеджер без Paid, нулевые суммы категории, единственная точка sparkline, отрицательная GP и одинаковые временные отметки не ломают UI/контракт.

## Реализация и проверка аналитики

Правила реализованы в Application/Reporting (PeriodResolver, MetricCalculator) и Application/Dashboard (DashboardQueryService). Предикат SQL — только Paid; активность менеджера не влияет на историческую аналитику. При отсутствии текущих Paid bestManagerId/bestManager/bestManagerDelta=null, bestManagerValue/bestManagerPrev=0; прошлый победитель не назначается текущим лидером.

Timezone конфигурируется IANA-именем либо UTC, по умолчанию Europe/Belgrade. Границы преобразуются отдельно: DST-день может содержать 23 или 25 часов. При пропущенной локальной полуночи используется первая существующая минута, при неоднозначной — первое наступление полуночи. Previous Period равен выбранному по календарным дням. Максимум — 366 дней, custom.from не раньше 1900-01-01, custom.to не позже отчётного today. Предыдущий диапазон может заходить до минимальной входной даты.

Все отношения и сортировки используют неокруглённые decimal. Округляется только результат: например, margin 1/300 и previous 1/600 дают отображаемые 0.33%, 0.17%, но marginDelta=0.17 pp (разность точных значений), а не 0.16. Это ожидаемое отличие от вычитания отображаемых чисел.

Тесты проверяют несколько позиций в чеке, Cancelled/Refunded, смену Paid→Refunded, бесплатную убыточную продажу, прошлые показатели того же лидера, tie-break по точному Average Check и UUID, границы с микросекундами, DST и независимость группировки от timezone PostgreSQL-сессии. На полном seed все шесть периодов сверены с независимым расчётом по исходным данным; пустой период возвращает нули. В production сырые продажи в память не загружаются.

## Уточнения REST-интеграции

from/to без preset теперь означают custom; preset и period — взаимоисключающие aliases. Все прежние границы/формулы сохраняются. Доли категорий вычисляет backend: 0 при нулевой сумме, GP share=null при отрицательной общей GP. Имя top-product — последнее ProductNameAtSale выбранной группы, а не текущее каталоговое имя. Рейтинг включает ежедневные ряды для frontend Comparison; финансовые расчёты и сортировка во frontend удалены. Подробный фактический контракт — 03-api.md.
