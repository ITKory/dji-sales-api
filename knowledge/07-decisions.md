# Технические решения и несовпадения

Дата: 2026-09-23. «Обязательное» ниже — прямое требование пользователя. «Предложено» — рабочее решение анализа, не согласованный ранее frontend HTTP-контракт. Реализованы доменная модель/Fluent API, миграции, seed и автоматический Compose bootstrap; dashboard API ещё не реализован. ADR-010 уточняет первоначальные проектные решения по индексам и именованию даты.

## ADR-001 — Read API поверх реальных позиций продаж

**Обязательное:** C#, .NET 8+, ASP.NET Core Web API, EF Core, PostgreSQL, Docker/Compose, async/await, REST. **Предложено:** сохранить net8.0 текущего проекта и одну production сборку с логическими слоями. Причина: небольшой аналитический сервис, нет оснований вводить распределённую архитектуру. Последствие: версии EF/Npgsql фиксировать совместимо, lifecycle выбранной .NET версии пересмотреть перед production deployment.

## ADR-002 — Пользовательские правила важнее mock

**Обязательное:** только Paid формирует выручку, себестоимость, прибыль, маржу, количество продаж, средний чек и рейтинги. Refunded полностью исключается. **Предложено:** в recent sales original amount сохраняется, признанная GP для Refunded/Cancelled=0. Последствие: mock отрицательная прибыль возврата не переносится, исторические метрики меняются после смены статуса. Движения по дате возврата потребуют другой модели.

## ADR-003 — Исторические цены и категории

**Предложено:** Sale + SaleItem, decimal/numeric, integer quantity, snapshots UnitSalePrice/UnitCost/CategoryIdAtSale/ProductNameAtSale. Причина: нельзя пересчитывать историю по текущему каталогу. Последствие: top-products имеет составной id для product/category и может показывать продукт в разных исторических категориях. Альтернатива объединения всех исторических категорий в текущую отвергнута из-за потери согласованности разрезов.

## ADR-004 — Календарный диапазон и timezone

**Обязательное:** включительные даты и непосредственно предшествующий период той же длины. **Предложено:** date-only query, DateOnly внутри сервиса, UTC timestamps в БД, Reporting__TimeZone=Europe/Belgrade, 366 дней максимум. ThisMonth = MTD, совпадает с resolvePeriod frontend. Причина: явные даты исключают browser/container timezone drift и ошибку округления миллисекунд. Последствие: timezone организации и лимит диапазона требуют подтверждения до запуска с реальными данными; конфигурация меняет календарные группировки.

## ADR-005 — Семантика процентов и отсутствующей базы

**Обязательное:** Margin=GP/Revenue, нулевая Revenue даёт Margin=0; нет Paid — Average Check=0. **Предложено:** API отдаёт margin в процентах, delta margin в pp; остальные delta null для ненулевого current при previous=0 и для previous<0, 0 для 0→0. Причина: нельзя выдавать фиктивные 100% роста. Последствие: расширить TS number до number|null и отрисовку «—», исправить обозначение marginDelta в KPI.

## ADR-006 — Leader и порядок результатов

**Предложено:** best manager по GP, затем AvgCheck, затем id; previous относится к тому же текущему победителю. В рейтинге только менеджеры с Paid, в comparison любой существующий. Топ продуктов по Revenue, затем GP, затем id. Причина: UI не задаёт эти tie/zero rules. Последствие: цифры mock bestManagerValue (184200 похоже на revenue, тогда как GP этого менеджера 77400) не являются эталоном.

## ADR-007 — DTO отделены от UI оформления

**Предложено:** явные Report<T>, camelCase, ISO даты, строковые enums, UUID, серверная пагинация. Category fill и форматированные даты остаются frontend; salesCount единообразен, legacy deals адаптируется. Причина: API не должен зависеть от CSS и локали. Последствие: потребуется небольшая интеграционная доработка frontend, одного совпадения имён полей недостаточно.

JSON numbers выбраны ради текущих TS number/Recharts. Денежные расчёты выполняет сервер; frontend не авторитетен для пересчёта/учёта. Numeric(18,2) шире точной целочисленной области JS: до production согласовать предельные суммы и при необходимости перейти на decimal strings + явное преобразование только для визуализации. Не обещать точность центов JS на любых допустимых БД значениях.

## ADR-008 — Согласованность без преждевременного кэша

**Предложено:** SQL aggregates, no tracking, scoped DbContext, последовательные async операции; snapshot в пределах каждого составного ответа. Причина: KPI/previous/sparkline должны согласовываться, общий DbContext нельзя использовать конкурентно. Последствие: несколько endpoints dashboard могут отражать разные моменты при обновлениях; общий snapshot endpoint добавлять при подтверждённой необходимости. Источник технического ограничения: [EF Core threading](https://learn.microsoft.com/en-us/ef/core/dbcontext-configuration/#avoiding-dbcontext-threading-issues).

## ADR-009 — Compose с раздельными стадиями инициализации

**Первоначально предложено (уточнено ADR-011):** postgres → migration job → API → nginx frontend; seed отдельно только development. Причина: воспроизводимый старт и отсутствие гонки миграций. Последствие: нужны health checks, migration bundle и внешний frontend build context/CI checkout. [Docker Compose conditions](https://docs.docker.com/compose/how-tos/startup-order/) позволяют ждать healthy service и успешный одноразовый job.

## Открытые предметные вопросы

Для продолжения проектирования приняты явно описанные значения, поэтому анализ не заблокирован. До production/импорта подтвердить timezone организации; USD и предельные суммы; смысл категорий; дату признания SaleDate против PaidAt; категорийные исторические снимки и повторные строки продукта; source of truth/способ импорта продаж; необходимость auth/multi-tenancy; допустимый размер периода; нужны ли отчёты «как было на дату» вместо текущего состояния статуса. Эти вопросы не отменяют обязательные пользовательские правила Paid/Refunded/дат.

## ADR-010 — Реализованная модель, связи и индексы

**Статус: реализовано.** Сущности и шесть конфигураций находятся в существующем Web API проекте; EF/Npgsql 8.0.11, отдельный SalesDbContext. Каноническое имя даты — `SaleDate` / `sale_date` вместо ранее предложенного SoldAt, семантика UTC instant сохранена.

Связи обязательные, с явными FK и `DeleteBehavior.Restrict`, включая Sale→SaleItem. Каскадное удаление менеджера/клиента/продукта/категории или самого чека могло бы уничтожить исторические факты. Удаление связанных строк БД отклоняет; для справочников Manager/Product предусмотрен IsActive без глобальных фильтров. У исторической категории позиции собственный FK, независимый от Product.CategoryId, поэтому перемещение продукта не переписывает прошлый разрез. Имена категорий уникальны, остальные бизнес-имена не считаются идентификаторами.

На sales выбраны три разных пути доступа:

1. `(Status, SaleDate)` — равенство по статусу и следующий диапазон дат. Это индекс для пары SaleDate+Status с порядком колонок под форму WHERE.
2. `(ManagerId, SaleDate)` — равенство/IN по менеджеру и даты. Полный индекс работает для любых статусов и обслуживает внешний ключ, в отличие от частичного Paid-индекса.
3. `(SaleDate DESC, Id DESC)` — общий список последних продаж и стабильное разрешение одинаковых дат. Отдельный `(SaleDate, Status)` не нужен без доказанной дополнительной нагрузки.

Для B-tree PostgreSQL 16 ведущие равенства и следующий диапазон определяют сканируемую часть индекса ([PostgreSQL multicolumn indexes](https://www.postgresql.org/docs/16/indexes-multicolumn.html)). Поэтому низкая кардинальность Status не мешает его использованию первым ключом вместе с датой, но отдельного индекса Status нет. Полные индексы выбраны вместо первоначально предложенных partial Paid: нет зависимости от способа параметризации фильтра и доступны отменённые/возвращённые продажи.

`UNIQUE (SaleId, LineNumber)` одновременно гарантирует однозначный порядок позиций и поддерживает join чека с позициями; повторный одиночный индекс SaleId не создан. Аналогично не дублируется ManagerId. Одиночные ProductId, CategoryIdAtSale, CustomerId и Product.CategoryId нужны для обратных связей и FK. Индексы не материализуют KPI; точность результатов обеспечивают сохранённые позиции и явная фильтрация Paid, а не отдельные колонки агрегатов.

Enums сохраняются строками с CHECK списка, деньги — numeric(18,2), все идентификаторы — uuid, SaleDate — timestamptz с запретом infinity. Это сохраняет читаемость БД и ограничения при записи вне EF. Модель допускает цену 0 и cost выше sale price: убыточная продажа валидна. CLR required/NOT NULL не заменяют будущую валидацию write-сценариев; ограничения минимум одной позиции, переходов статуса и неизменяемости снимков относятся к следующему слою приложения.

Проверка: интеграционные тесты на PostgreSQL, включая FK/RESTRICT, round-trip и historical snapshots. Производительность индексов на production объёме пока не измерена; новые частичные/покрывающие индексы добавлять по EXPLAIN ANALYZE, а не дублировать заранее.

## ADR-011 — Детерминированный demo dataset и автоматическая инициализация

**Статус: реализовано по текущему требованию.** Compose запускает PostgreSQL 16.15-alpine → database-init → API. `database-init` является CLI-режимом опубликованного приложения, выполняющим миграции и seed последовательно; это заменяет ранее предложенные отдельный migration bundle и seed dev-profile. Причина: одна команда `docker compose up --build` должна сразу давать наполненную БД, без ручного запуска дополнительного profile/job. Runtime image одинаковый, SDK/EF CLI в production-слой не добавляются. Frontend-контейнер по-прежнему вне текущего этапа.

EF Core 8 не предоставляет migration locking более новых версий ([Microsoft: applying migrations](https://learn.microsoft.com/en-us/ef/core/managing-schemas/migrations/applying)). Поэтому initializer явно держит `pg_advisory_lock(78234001)` на одном физическом соединении вокруг MigrateAsync и seed. DemoSeeder дополнительно держит транзакционную `pg_advisory_xact_lock(78234002)` на check+insert; это защищает прямые конкурентные вызовы seeder. Семантика session/transaction locks описана в [PostgreSQL advisory locks](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS). Ручной EF CLI не должен работать одновременно с initializer, потому что не использует эти locks.

Выбран фиксированный набор sales-demo-v1: Random(20260923), UUID по детерминированной схеме, 365 дней 2025-09-24—2026-09-23. Отвергнуто исходное предложение default anchor=today: оно давало бы разные базы при первом запуске в разные дни и нарушало бы полную воспроизводимость. Следствие: demo со временем «стареет»; для его просмотра выбирать исторический custom range. Операционный applied_at остаётся реальным UTC-временем и не входит в business fingerprint.

Объём 20/80/6/48/3600 (менеджеры/клиенты/категории/продукты/продажи) обеспечивает несколько тысяч чеков, разные группы менеджеров, сезонность, чек/маржу, отмены/возвраты и явные пустые периоды. Снимки цены/себестоимости создаются в позициях; финансовые агрегаты не seed-ятся отдельно. Изменение содержимого требует новой версии, а не незаметной правки генератора v1.

Маркер seed_history и все domain inserts записываются одной транзакцией. Маркер есть → no-op, правки пользователя сохраняются. Маркера нет и данные уже есть → явная ошибка, отключить demo seed для использования этой БД. Частичный сбой → rollback seed, retry возможен; уже успешная миграция не откатывается. Нет автоматической чистки/ремонта БД. Данные живут в named volume; повторный up/down без -v их сохраняет.

**Refunded окончательно:** полное исключение чека из всех метрик, включая Cost/SalesCount и исторический период SaleDate; не отрицательная продажа. В Recent Sales original amount сохраняется, признанная GP=0. Это зафиксировано отдельным разделом 04-business-rules.md и не подменяется mock отрицательной прибылью возвратов.

Проверено: 28 PostgreSQL тестов, два новых database fingerprints, параллельные initializers, rollback после фактических inserts, повторное выполнение с сохранением пользовательских правок. Compose cold start и повторный build/up прошли; fingerprints всех шести таблиц и applied_at не изменились, API readiness 200. Размеры таблиц/статусы сверены SQL. Npgsql/EF модели и migration snapshot совпадают.

## ADR-012 — Одно SQL-чтение и Application-композиция аналитики

**Статус: реализовано.** Для KPI и динамики выбран параметризованный PostgreSQL CTE через EF Core 8 `Database.SqlQuery<ManagerDailyAggregate>`. EF поддерживает [SQL для unmapped CLR types](https://learn.microsoft.com/en-us/ef/core/what-is-new/ef-core-8.0/whatsnew#raw-sql-queries-for-unmapped-types); DTO не становится entity. Dapper не добавлен: отдельная зависимость и управление соединением не дают выигрыша для одного запроса.

Причина SQL: явно контролировать агрегацию позиций сначала на уровне чека (COUNT не умножается на позиции), затем менеджера/дня, timezone и чтение current+previous одним statement. Три параметра — timezone, startUtc, endExclusiveUtc; Paid — постоянный SQL literal. Пользовательские значения не конкатенируются. Группировка использует [AT TIME ZONE](https://www.postgresql.org/docs/16/functions-datetime.html#FUNCTIONS-DATETIME-ZONECONVERT), а WHERE сравнивает исходный timestamptz с UTC-границами, сохраняя возможность использовать индекс (status,sale_date). JOIN sale_items использует существующий индекс sale_id. Новые индексы и миграции без измеренной необходимости не добавлены.

Все денежные суммы считаются в PostgreSQL numeric; в Application приходят decimal агрегаты менеджер/день. Application объединяет их, вычисляет margin/avgCheck/delta, выбирает лидера и заполняет нули. Это серверная обработка ограниченного набора агрегатов без N+1 и загрузки истории в память. Один statement в PostgreSQL [Read Committed видит согласованный снимок](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-READ-COMMITTED), поэтому для этого отчёта не нужна отдельная repeatable-read транзакция. Отчёты между вызовами не обещают общий snapshot.

PeriodResolver и MetricCalculator перенесены из Infrastructure в Application: календарь и правила прибыли не зависят от persistence. IAnalyticsReader инвертирует зависимость, TimeProvider делает today воспроизводимым в тестах. Разрешены IANA timezone/UTC, поддержаны DST и локальная полночь; границы включительны на уровне дат, полуоткрыты на уровне UTC.

Проверка: 40 unit и 35 PostgreSQL integration tests прошли. SQL interceptor подтверждает один SELECT и три параметра на отчёт; независимый расчёт полного seed подтверждает агрегаты всех периодов. Производительность на production-объёмах не измерялась; при росте количества менеджеров/дней потребуется профилирование перед введением materialized views или дополнительных индексов.

## ADR-013 — Шесть REST routes и интеграция dashboard

**Реализовано по запросу пользователя:** /api/analytics/kpi, managers/ranking, dynamics, categories, products/top, sales/recent. Прежние маршруты были планом и не использовались frontend; compatibility redirects не нужны. Поддержаны preset/period (взаимоисключающие aliases), from/to без preset выводит custom. Строгий parser не допускает неизвестные/повторные/пустые query и числовые enum. Ошибки — ProblemDetails с code/traceId и полем ошибки, без SQL/secrets.

Для сохранения существующей вкладки Comparison ответ рейтинга включает timeSeries каждого менеджера. Эти агрегаты уже получены одним запросом; дополнительных запросов на менеджера нет. Компромисс — более крупный ответ и доступность Comparison только для текущего рейтинга. Lookup неактивных/непродававших менеджеров остаётся отдельным будущим scope.

Категории возвращают рассчитанные в PostgreSQL доли; top-products группируются по historical category и выбирают последнее snapshot-имя. Recent count/page читаются двумя запросами в Repeatable Read (в отличие от одноstatement KPI), что сохраняет согласованный totalCount и items даже при конкурентной записи. LIMIT/OFFSET применяются до агрегации позиций страницы. Новые индексы не добавлены: используются существующие sales(status,sale_date), sales(sale_date,id) и sale_items(sale_id).

Frontend использует same-origin /api через Vite dev/preview proxy; открывать CORS не требуется. AbortController + request key защищают от устаревших ответов, ошибка показывается отдельно от пустых данных. Форматирование/визуальный масштаб остаются в UI, метрики/доли/сортировка/page totals — на сервере. Production deployment frontend требует reverse proxy /api; Compose пока запускает PostgreSQL/init/API.
