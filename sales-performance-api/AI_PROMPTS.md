Codex
1)Ты работаешь над backend частью тестового задания Sales Performance Dashboard.

Стек:
- C#
- .NET 8+
- ASP.NET Core Web API
- Entity Framework Core
- PostgreSQL
- async/await
- Docker Compose

Frontend уже реализован, поэтому сначала изучи его API-вызовы, типы и ожидаемые DTO. Не меняй frontend без явного запроса.

Основные требования:
- backend должен выполнять фильтрацию и агрегирование на сервере;
- нельзя загружать тысячи продаж во frontend для пересчёта;
- нужны понятные REST API-контракты;
- нужны EF Core migrations;
- нужна воспроизводимая seed-генерация;
- нужно избежать N+1;
- все операции с БД должны быть асинхронными;
- обязательны обработка ошибок, валидация и пустые результаты;
- авторизация не нужна;
- решение должно запускаться через docker compose up --build.

Перед изменением кода:
1. изучи существующую структуру проекта;
2. найди frontend API-контракты;
3. проверь, какие части backend уже созданы;
4. не создавай лишние архитектурные слои без необходимости;
5. после работы запусти доступные build и test-команды.

Не переписывай рабочий код без причины. Если обнаружишь противоречие между заданием и frontend-контрактом, сначала объясни его и выбери совместимое решение.

3)На основе анализа реализуй backend-модель данных для Sales Performance Dashboard.

Нужно проверить или создать:
- Manager;
- Customer;
- Category;
- Product;
- Sale;
- SaleItem;
- enum статусов продажи: Paid, Cancelled, Refunded.

Требования:
- корректные связи и foreign keys;
- подходящие типы данных для денег и дат;
- decimal precision для денежных значений;
- required-поля и ограничения длины;
- индексы для частых фильтров и аналитических запросов;
- конфигурация Entity Framework Core через Fluent API;
- DbContext;
- EF Core migration;
- автоматическое применение migration при запуске backend;
- воспроизводимый seed.

Seed должен содержать реалистичные данные:
- 15–25 менеджеров;
- 50–100 клиентов;
- несколько категорий;
- несколько десятков товаров;
- 2 000–5 000 продаж;
- период минимум 12 месяцев;
- Paid, Cancelled и Refunded;
- разные показатели менеджеров;
- сезонность;
- разные средние чеки и маржинальность;
- крупные и мелкие сделки;
- хотя бы у некоторых менеджеров периоды без продаж.

Seed должен быть deterministic: пересоздание базы должно давать одинаковые данные.

Не используй случайность без фиксированного seed. Не создавай дубликаты при повторном запуске приложения.

После реализации выполни build и доступные проверки. Отдельно объясни, какие индексы добавлены и почему.
4)Реализуй REST API для готового фронтенда.

Сначала найди реальные API-вызовы frontend и сопоставь их с backend-контрактами. Не создавай абстрактный API, если frontend уже ожидает конкретные пути, параметры или названия полей.

Для каждого endpoint обеспечь:
- валидацию дат;
- включительный диапазон дат;
- понятные query-параметры;
- корректные HTTP status codes;
- единый формат ошибок;
- cancellation token;
- async/await;
- отсутствие N+1;
- корректный пустой ответ без 500 ошибки.

Минимально должны быть доступны данные для:
- KPI;
- динамики;
- рейтинга менеджеров с режимами Gross Profit и Average Check;
- категорий и продуктов;
- последних продаж.

Если frontend ожидает один агрегированный endpoint dashboard, предпочти его отдельным endpoint для каждого блока, чтобы смена периода выполнялась согласованно. Если frontend уже использует несколько endpoints, сохрани совместимость.

Добавь:
- DTO;
- контроллеры;
- query-модели;
- валидацию;
- глобальную обработку неожиданных ошибок;
- Swagger, если он уже предусмотрен проектом.

Отдельно проверь timezone и формат дат. Зафиксируй принятое решение в knowledge/03-api.md и knowledge/07-decisions.md.

После реализации проверь API локально или интеграционными тестами. Обнови changelog.md.
